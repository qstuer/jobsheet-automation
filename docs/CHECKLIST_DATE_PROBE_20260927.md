# PM 檢查表跨頁日期，只讀全樣本試驗（2026-09-27）

目的：調查完整單據 B01、B04、B06、B07、B10 因首頁日期辨識不穩而停下，能否安全使用後續 PM 檢查表日期。模型只看單一固定日期欄；人工答案只在讀完後匿名評分，沒有提供 Asana 候選或答案。沒有上傳、移動或改名任何正式檔案。

試驗在獨立分支進行：[第一次](https://github.com/qstuer/jobsheet-automation/actions/runs/36298225495)、[分開評分的第二次](https://github.com/qstuer/jobsheet-automation/actions/runs/36298522877)。第二次有 16 張已核實的完整 PM、3 張缺頁跳過、1 張答案未核實跳過；64 次模型調用，DeepSeek 費用保守上限約 ¥0.053。

這五張停下的完整單據（B01、B04、B06、B07、B10）在第二次試驗中，第一張檢查表的日期均讀對。然而，B08、B09、B19 的檢查表首頁日期沒有正確核實；B19 的兩處甚至一致地讀錯。第一次只有 3 張兩處一致且正確，第二次為 4 張，亦顯示圖片模型讀數不穩定。**不能把「兩次讀一樣」或「兩頁讀一樣」直接當成日期真實性的證明。**末頁印章覆蓋簽署資料，不能成為每張單的必要條件。

目前不改正式配對。候選的下一條通用規則須同時滿足：

1. 只在既有流程已停下時作後備，絕不覆蓋已可靠選對的工作。
2. 第一張檢查表日期雙讀一致，並獲首頁 ACTION DATE 或首頁客戶簽署日期的獨立同值支持；有明確衝突便停下。Asana 日期只用於之後核對，不能替 OCR 填答案。
3. 設備身分、PM／CM、Asana 正式到期／完成日期及同設備其他歷史工作仍獨立檢查；不能只因日期接近就接受一字錯誤的機身編號。
4. 在同一 20 張和之後未用來設計規則的新單據上驗證，要求錯誤自動匹配為零；缺頁及答案未核實者分開計數。通過前維持只讀，不接 OneDrive。
